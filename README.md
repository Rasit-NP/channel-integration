# 숙박 상품 채널 연동 백엔드

여러 외부 숙박 상품 공급사(Supplier)의 서로 다른 API 를 하나의 일관된 숙박 상품 모델로
통합해, 고객에게 **출처와 무관하게 동일한 형태의 검색 결과**를 제공하는 연동 백엔드입니다.

공급사마다 같은 객실을 다르게 표현합니다. 어떤 곳은 날짜별 1박 단가를 세금 별도로 주고,
어떤 곳은 숙박 전체 총액만 세금 포함으로 줍니다. 실패를 HTTP 상태 코드로 알리는 곳이 있고,
항상 200 을 주면서 응답 본문의 코드로만 알리는 곳도 있습니다. 이 차이를 어댑터 계층에서
흡수하는 것이 이 시스템의 핵심입니다.

---

## 구현 현황

이 문서에 적은 설계는 아래 상태를 정확히 반영합니다. **설계만 하고 구현하지 않은 항목은
그렇게 표시**했습니다.

| 항목 | 상태 |
| --- | --- |
| 프로젝트 스캐폴딩 · 빌드 구성 | ✅ 구현 |
| MVC + WebClient 스택 고정 (§기술 스택) | ✅ 구현 |
| 통합 상품 모델 · 공급사 연동 경계 | ✅ 구현 |
| Mock Supplier (정상/장애/무응답 3모드) | ✅ 구현 |
| 공급사 A 어댑터 | ✅ 구현 |
| 연동 견고성 — 타임아웃 · 실패 판정 통일 | ✅ 구현 |
| 매핑 저장 — 스키마 · 저장소 | ✅ 구현 |
| 숙소 목록 동기화 — 기동 · 주기 · 수동 | ✅ 구현 |
| 통합 검색 API | ✅ 구현 |
| 연동 견고성 — 병렬 호출 · 부분 실패 병합 | ✅ 구현 |
| 공급사 B 어댑터 | ✅ 구현 |

테스트 124개가 이 상태를 지키고 있습니다.

**핵심 흐름은 끝까지 돕니다** — 공급사 숙소 목록 조회 → 매핑 저장 → 검색 요청 → 묶음 분할 →
병렬 조회 → 정규화 → 병합 → 응답. 공급사가 둘이므로 **실패 판정 통일과 부분 실패가 실제로
관측됩니다** — A 는 503 으로, B 는 200 + 본문 코드로 실패를 알리는데 응답에는 같은 사유가
나가고, 한쪽이 죽어도 나머지 결과로 응답합니다.

**B 를 붙이며 `domain`·`application`·`api` 는 한 줄도 고치지 않았습니다.** 늘어난 것은
`adapter/b/` 패키지와 설정뿐입니다(§신규 공급사 추가 방법).

## 빌드 및 실행

JDK 21 이 필요합니다. Gradle 은 wrapper 를 사용하므로 별도 설치가 필요하지 않습니다.

```bash
./gradlew build
```

```bash
./gradlew bootRun
```

기동하면 Tomcat 이 `8080` 포트로 뜨고, `./data/` 에 H2 파일이 생기면서 매핑 테이블이
만들어집니다(§저장 정책).

Mock Supplier 는 **별도 프로세스**로 띄웁니다. 본 애플리케이션과 같은 포트에 두면 안 됩니다
(§Mock Supplier). 공급사 목록을 받아오려면 이쪽이 먼저 떠 있어야 합니다.

```bash
./gradlew :mock-supplier:bootRun
```

검색은 매핑이 채워져 있어야 결과를 냅니다. 매핑이 비어 있으면 물어볼 숙소가 없다는 뜻이라
공급사를 부르지 않고 빈 결과를 줍니다 — 실패가 아닙니다.

### 동기화 확인해 보기

기동하면 자동으로 한 번 돕니다(§숙소 목록을 언제 동기화하는가). 기다리지 않고 직접 돌리려면:

```bash
curl -X POST http://localhost:8080/internal/suppliers/sync
```

```jsonc
{
  "suppliers": [
    { "supplier": "A", "status": "OK", "properties": 2, "roomTypes": 2 },
    { "supplier": "B", "status": "OK", "properties": 1, "roomTypes": 1 }
  ],
  "properties": 3, "roomTypes": 3,
  "partial": false
}
```

Mock 을 띄우지 않고 앱만 기동해도 **애플리케이션은 정상적으로 뜹니다.** 공급사에 닿지 못한
것이 기동 실패가 되어서는 안 되기 때문입니다. 그때는 위 응답의 `partial` 이 `true` 가 되고
`status` 가 `FAILED` 로 나옵니다.

### 검색해 보기

```bash
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
```

Mock 기본 데이터로는 **두 공급사에서 하나씩** 나옵니다. A 의 나머지 하나는 09-02 재고가 0 이라
빠지고, 빠졌다는 사실이 `excludedSoldOut` 에 남습니다(§재고 판정).

**두 상품은 같은 이름의 숙소입니다.** 합치지 않고 각각 노출하며(§동일 숙소를 병합하지 않는 이유),
요금과 함께 조식 포함 여부가 보이므로 무엇이 포함된 값인지 비교할 수 있습니다.

```jsonc
{
  "stays": [
    {
      "propertyId": 1, "propertyName": "Riverside Hotel Seoul",
      "roomTypeId": 1, "roomTypeName": "Deluxe Twin",
      "maxOccupancy": 2, "availableRooms": 1,        // 재고 3/1/5 의 최솟값
      "supplier": "A", "breakfastIncluded": false,
      "price": { "totalAmount": 429000, "currency": "KRW", "taxAmount": 39000,
                 "nightlyRates": [ /* 3박치 */ ] }
    },
    {
      "propertyId": 3, "propertyName": "Riverside Hotel Seoul",
      "roomTypeId": 3, "roomTypeName": "Deluxe Twin Room",
      "maxOccupancy": 2, "availableRooms": 1,
      "supplier": "B", "breakfastIncluded": true,
      "price": { "totalAmount": 452000, "currency": "KRW" }   // 세액·내역 필드가 아예 없다
    }
  ],
  "suppliers": [ { "supplier": "A", "status": "OK" }, { "supplier": "B", "status": "OK" } ],
  "partial": false,
  "excludedSoldOut": 1, "excludedUnmapped": 0, "excludedOverCapacity": 0
}
```

한쪽을 고장내도 **응답은 200 이고, 살아 있는 공급사의 결과는 그대로 나옵니다**(§부분 실패 허용).

```bash
curl -X POST 'http://localhost:9090/control/a/mode?value=error'
```

```jsonc
{
  "stays": [ /* B 의 상품 1건 */ ],
  "suppliers": [
    { "supplier": "A", "status": "FAILED", "reason": "SUPPLIER_ERROR" },
    { "supplier": "B", "status": "OK" }
  ],
  "partial": true,
  "excludedSoldOut": 0, "excludedUnmapped": 0, "excludedOverCapacity": 0
}
```

**두 공급사를 함께 고장내면 실패 판정 통일이 보입니다.** A 는 503 으로, B 는 200 + 본문 코드로
알리는데 응답에 나가는 사유는 둘 다 `SUPPLIER_ERROR` 입니다(§실패 판정 통일).

```bash
curl -X POST 'http://localhost:9090/control/b/mode?value=error'
```

### 설정

| 키 | 기본값 | 뜻 |
| --- | --- | --- |
| `supplier.sync.on-startup` | `true` | 기동 직후 1회 동기화 여부 |
| `supplier.sync.interval` | `1h` | 주기적 갱신 간격 |
| `supplier.a.base-url` | `http://localhost:9090` | 공급사 A 주소 (Mock) |
| `supplier.a.api-key` | `local-dev-key` | 공급사 A 인증 키 |
| `supplier.a.connect-timeout` | `2s` | 연결 제한 (§타임아웃) |
| `supplier.a.response-timeout` | `3s` | 응답 제한 (§타임아웃) |
| `supplier.a.max-batch-size` | `50` | 한 번에 조회할 숙소 코드 수 상한 |
| `supplier.b.base-url` | `http://localhost:9090` | 공급사 B 주소 (Mock) |
| `supplier.b.api-key` | `local-dev-key` | 공급사 B 인증 키 |
| `supplier.b.connect-timeout` | `2s` | 연결 제한 (§타임아웃) |
| `supplier.b.response-timeout` | `3s` | 응답 제한 (§타임아웃) |
| `supplier.b.max-batch-size` | `50` | 한 번에 조회할 숙소 코드 수 상한. **값은 어댑터마다 따로 선언**하므로 공급사끼리 달라도 됩니다 |
| `supplier.search.max-concurrency` | `4` | 한 공급사에 동시에 띄우는 묶음 호출 수 상한 |
| `supplier.search.timeout` | `5s` | 검색 전체 상한 (§검색 전체에도 상한을 둔다) |

## 기술 스택

| 항목 | 값 |
| --- | --- |
| Language | Java 21 |
| Framework | Spring Boot 3.5.16 |
| Build | Gradle (Kotlin DSL) |
| HTTP Client | WebClient (외부 공급사 연동 전용) |
| Web Stack | Spring MVC (Servlet) |
| Database | H2 (§저장 정책) |

위 항목은 [build.gradle.kts](build.gradle.kts) 에 반영되어 있습니다.

**WebFlux 는 전면 도입하지 않습니다.** 통합 검색 API 는 MVC 로 서빙하고, WebClient 는 공급사
호출에만 씁니다. 그래서 `spring-boot-starter-webflux` 는 클래스패스에 있지만 웹 스택으로는
쓰지 않습니다.

이 상태는 자동 판정에 맡기지 않고 코드에 고정했습니다.
[application.yaml](src/main/resources/application.yaml) 의
`spring.main.web-application-type: servlet` 이 그 장치입니다. web 과 webflux 가 함께 있으면
웹 스택이 자동으로 결정되는데, 지금은 서블릿으로 떠도 이후 의존성이 바뀌면 조용히 리액티브로
넘어갈 수 있습니다. 그때 바뀐 것을 알아채기 어렵기 때문에 값을 명시해 두었습니다.

## 통합 상품 모델

### 표준 요금을 무엇으로 잡을 것인가

두 공급사의 요금 표현이 비대칭입니다.

| | 공급사 A | 공급사 B |
| --- | --- | --- |
| 단위 | 날짜별 1박 단가 | 숙박 전체 총액 |
| 세금 | 별도(net) — 세액을 따로 준다 | 포함(gross) — 세액을 주지 않는다 |

**변환은 한쪽 방향으로만 가능합니다.** A 의 날짜별 `(단가 + 세액)` 을 합치면 세금 포함 총액이
나옵니다. 반대로 B 의 총액을 날짜별로 쪼개거나 세액을 분리하는 것은 **불가능**합니다. 임의로
1/N 하면 실제와 다른 값을 만들어내는 것이고, 그건 정규화가 아니라 날조입니다.

그래서 **표준은 "숙박 기간 전체 총액, 세금 포함(gross)"** 으로 잡습니다. 두 공급사가 모두
정확히 표현할 수 있는 유일한 지점입니다.

```
totalAmount   : 요청 기간 전체 결제 예정 금액 (세금 포함)   [필수]
currency      : ISO 4217                                    [필수]
nightlyRates[]: 날짜별 요금 내역                            [선택 · 제공하는 공급사만]
taxAmount     : 세액                                        [선택 · 제공하는 공급사만]
```

**무엇을 잃는가.** 이 선택으로 잃는 것을 알고 택했습니다.

- B 상품은 날짜별 요금을 알 수 없습니다. "1박만 취소 시 환불액", "특정 날짜만 비교" 같은
  기능은 B 상품에 대해 불가능합니다.
- B 상품은 세액을 분리할 수 없습니다. 영수증에 세금을 따로 표시해야 한다면 A 만 가능합니다.
- 선택 필드가 공급사에 따라 비므로, 이 필드를 쓰는 기능은 "없을 수 있음"을 항상 처리해야
  합니다.

**필드 단위 대응표와 손실 정보 전체 목록은
[docs/integration-model.md](docs/integration-model.md) 에 있습니다.** 위 셋은 표준을 정할 때 알고
택한 것이고, 그 문서에는 필드를 하나씩 대조하다 드러난 것들이 함께 있습니다.

대안으로 **날짜별 단가를 표준으로** 삼는 안을 검토했다가 버렸습니다. B 의 총액을 날짜 수로
나누는 순간 없는 정보를 지어내게 되고, 그 값이 고객에게 노출되면 실제 결제액과 어긋납니다.
정보를 잃는 것보다 지어내는 것이 훨씬 나쁩니다.

### 총액은 요청 기간에 대해서만 만듭니다

총액은 **요청한 숙박일의 요금을 합친 값**입니다. 공급사가 어떤 날짜를 보냈는지와는 별개입니다.

당연해 보이지만 저절로 되지는 않습니다. 공급사가 요청 기간보다 넓은 날짜를 돌려주면, 받은 것을
그대로 합산하는 구현은 **하루치를 더 청구합니다.** 재고 판정은 요청 기간을 알고 있어서 걸러내는데
요금만 모르고 있으면, 재고는 맞고 금액만 틀린 응답이 나갑니다. 게다가 `nightlyRates` 의 합은
`totalAmount` 와 여전히 일치하므로 **응답만 봐서는 틀린 것을 알 수 없습니다.**

기간과 어긋나는 두 방향을 다르게 다룹니다.

| 어긋남 | 처리 | 왜 |
| --- | --- | --- |
| 요청 기간 **밖의** 날짜를 더 줬다 | 버린다 | 숙박에 포함되지 않는 날입니다. 버려도 잃는 것이 없습니다 |
| 숙박일 하나의 요금이 **없다** | 그 상품을 만들지 않는다 | 있는 것만 더하면 과소 청구고, 채우려면 없는 값을 지어내야 합니다 |

같은 숙박일이 두 번 오는 경우도 거부합니다. 어느 쪽이 맞는지 알 수 없는데 그냥 더하면 하루치를
두 번 청구합니다.

이 규칙을 **어댑터가 아니라 도메인(`StayPrice`)에 둔 것**이 핵심입니다. 어댑터에 두면 공급사마다
같은 규칙을 기억해야 하고, 새 공급사를 붙이며 빠뜨려도 컴파일러도 테스트도 잡아주지 않습니다.
요금 팩토리가 요청 기간을 **요구하게** 하면 기간 없이는 요금을 만들 수 없습니다. 재고를
`Availability.forStay(재고, 기간)` 가 판정하는 것과 같은 모양입니다.

§인원 초과 상품을 우리도 한 번 더 거릅니다 와 같은 기조입니다 — **상대가 계약을 지킨다고 가정하지
않습니다.** 다만 여기서는 "틀리면 거른다"가 아니라 "우리 기준으로 다시 센다"입니다.

### 조건이 다른 상품을 어떻게 다루는가

같은 객실인데 A 429,000원 / B 452,000원처럼 총액이 다를 수 있습니다. 그런데 이건 단순한
가격 차가 아닙니다 — **B 는 조식 포함, A 는 미포함**입니다. 조건이 다른 상품입니다.

따라서 `breakfastIncluded` 를 **요금과 같은 층위의 표준 필드**로 둡니다. 요금만 노출하고
조건을 빼면 고객이 "싼 쪽"을 고르는 순간 다른 상품을 비교하게 됩니다. 값이 싸다는 사실보다
**무엇이 포함된 값인지**가 함께 보여야 비교가 성립합니다.

### 동일 숙소를 병합하지 않는 이유

A 와 B 가 실제로 같은 숙소를 취급해도, 이를 알려주는 공통 키가 스펙에 없습니다. 숙소명과
객실 구성으로 추정하는 수밖에 없는데, 추정이 틀리면 **다른 숙소를 하나로 합쳐 파는** 사고가
됩니다. 잘못 합치는 비용이 안 합치는 비용보다 큽니다.

그래서 **공급사가 다르면 내부 식별자도 다르게** 부여하고, 두 상품을 각각 노출합니다.
고객에게는 "같은 이름의 숙소가 조건이 다른 두 상품으로 보인다"가 되는데, 조식 포함 여부가
함께 노출되므로 이해 가능한 화면이 됩니다.

여기서 반드시 지켜야 하는 것은 **같은 공급사의 같은 상품이 언제 조회해도 같은 내부 식별자로
돌아오는 것**입니다. 이건 매핑 테이블의 unique 제약으로 보장합니다.

## 재고 판정

### 연박 예약 가능 객실 수

공급사는 **날짜별** 잔여 객실 수를 줍니다. 3박을 예약하려면 그 객실 타입을 **3일 연속** 확보해야
하므로, 예약 가능 객실 수는 요청 기간 각 숙박일 잔여 수의 **최솟값**입니다.

```
availableRooms = min(각 숙박일의 remainingRooms)
```

예를 들어 잔여가 `2 / 0 / 4` 인 객실 타입은 중간 하루가 0 이므로 3박 연속 예약이 불가능합니다.
합계(6)나 평균(2)으로 판정하면 예약할 수 없는 상품을 예약 가능으로 노출하게 됩니다.
**병목이 되는 하루가 전체를 결정**합니다.

응답 기간에 해당하는 날짜가 하나라도 빠져 있으면 그 날은 재고 0 으로 봅니다. 알 수 없는 것을
있다고 가정하지 않습니다.

### 예약 불가 상품은 응답에서 제외

`availableRooms` 가 0 인 상품은 검색 결과에서 **뺍니다.** 검색 API 의 계약을 "예약 가능한
상품 목록"으로 정의했기 때문입니다. 0 은 예약 불가이므로 결과가 아닙니다.

다만 제외했다는 사실 자체는 응답 메타에 남깁니다. 판정이 동작했는데 결과가 비었는지, 아니면
공급사 조회가 실패해서 비었는지를 클라이언트가 구분할 수 있어야 합니다.

### 무엇을 왜 뺐는지 세 가지로 나눠 셉니다

결과에서 빠지는 이유는 셋이고, 각각 클라이언트가 할 일이 다릅니다.

| 필드 | 뺀 이유 | 이게 크면 |
| --- | --- | --- |
| `excludedSoldOut` | 요청 기간 중 하루라도 재고가 0 | 정상입니다. 날짜를 바꾸면 됩니다 |
| `excludedUnmapped` | 공급사가 줬지만 우리 매핑에 없음 | **우리 문제입니다.** 동기화가 밀렸다는 신호 |
| `excludedOverCapacity` | 요청 인원을 수용하지 못함 | 인원을 줄이거나, 공급사가 계약을 안 지킨 것 |

하나로 합치면 "결과가 비었다"까지만 알 수 있습니다. 셋으로 나누면 **누가 무엇을 해야 하는지**가
갈립니다. 특히 `excludedUnmapped` 는 고객이 아니라 우리가 고칠 문제라 구분해 둘 값어치가 있습니다.

### 인원 초과 상품을 우리도 한 번 더 거릅니다

공급사는 요청 인원을 수용할 수 있는 객실 타입만 준다고 되어 있습니다. 그래도 `maxOccupancy` 를
다시 확인합니다.

재고 날짜가 빠졌을 때 0 으로 보는 것과 같은 기조입니다 — **상대가 계약을 지킨다고 가정하지
않습니다.** 이 검사가 없으면 공급사가 계약을 어겼을 때 4명이 묵을 수 없는 방을 4명에게 팔게
되는데, 그 사고의 비용이 검사 한 줄보다 훨씬 큽니다.

## 연동 견고성

### 실패 판정 통일

공급사마다 실패를 알리는 방식이 다릅니다.

| | 실패 통지 방식 |
| --- | --- |
| 공급사 A | HTTP 상태 코드 (4xx / 5xx) |
| 공급사 B | **항상 HTTP 200** + 응답 본문의 결과 코드 |

B 는 장애 상황에서도 HTTP 200 을 주기 때문에, 상태 코드만 보면 **장애를 정상 응답으로 처리**하게
됩니다. 이건 조용히 잘못된 결과를 내보내는 종류의 버그라 가장 위험합니다.

그래서 실패 판정을 어댑터 안으로 넣고, 두 방식을 **같은 실패 타입 하나**로 정규화합니다.
도메인 계층은 "A 는 상태 코드, B 는 본문 코드"라는 사실을 알지 못합니다. 공급사가 늘어도
도메인은 그대로입니다.

**전송 계층의 실패는 여전히 공통입니다.** 연결이 안 되거나 응답이 늦거나 인프라가 5xx 를 내는
것은 어느 공급사에게나 똑같이 생기는 일이라 두 어댑터가 같은 코드를 씁니다. B 도 상태 코드 판정을
버리는 게 아니라, **그 위에 본문 코드 판정을 얹습니다.** 층이 다릅니다.

**두 방식이 같은 해상도로 정규화됩니다.** A 가 상태 코드로 구분하는 것(잘못된 요청 400, 인증 실패
401, 호출 한도 초과 429)을 B 는 결과 코드로 구분합니다. 통지 수단이 다를 뿐 담기는 정보가 줄지
않아야 "같은 실패로 정규화했다"가 성립합니다 — 전부 `SUPPLIER_ERROR` 로 뭉개면 클라이언트는 인증
문제에 재시도를 걸고 한도 초과에 즉시 재시도를 겁니다.

### 타임아웃

| 구간 | 값 | 근거 |
| --- | --- | --- |
| 연결(connect) | 2초 | 정상적인 TCP 핸드셰이크는 수십 ms 안에 끝납니다. 2초를 넘겼다면 네트워크 경로 이상으로 보고 끊는 편이 낫습니다 |
| 응답(response) | 3초 | 공급사 호출은 병렬이므로 **가장 느린 공급사가 전체 응답 시간을 결정**합니다. 검색 응답 목표를 5초 안쪽으로 두고, 정규화·병합 오버헤드를 남겨 3초로 잡았습니다 |

두 값 모두 **근거 있는 초기값이지 측정된 값은 아닙니다.** 실제 공급사의 응답 시간 분포를
관측하면 p99 기준으로 다시 잡아야 합니다. 지금은 관측할 실제 공급사가 없으므로 위 근거로
고정하고, 설정으로 빼서 코드 수정 없이 바꿀 수 있게 합니다.

**다시 잡는 절차와 세 상한(연결·응답·검색 전체) 사이의 부등식은
[docs/observability.md](docs/observability.md) 에 있습니다.** 거기서 계산해 보면 현재 기본값으로는
**숙소가 200개를 넘는 순간부터** 검색 전체 상한에 걸리기 시작합니다.

### 부분 실패 허용

한 공급사가 죽어도 **나머지 공급사의 결과로 응답**합니다. 전체를 실패로 만들면 공급사 하나의
장애가 서비스 전체 장애가 됩니다.

응답은 HTTP 200 이고, 본문에 공급사별 조회 상태를 함께 담습니다. 부분 실패는 오류가 아니라
**불완전한 성공**이므로, 클라이언트가 결과의 완전성을 스스로 판단할 수 있어야 합니다.

```jsonc
{
  "stays": [ /* ... */ ],
  "suppliers": [
    { "supplier": "A", "status": "OK" },
    { "supplier": "B", "status": "FAILED", "reason": "TIMEOUT" }
  ],
  "partial": true,
  "excludedSoldOut": 2,       // 재고 0 으로 제외 (§재고 판정)
  "excludedUnmapped": 0,      // 매핑에 없어 제외
  "excludedOverCapacity": 0   // 인원 초과로 제외
}
```

`excluded*` 가 §재고 판정에서 말한 "제외했다는 사실"을 담는 자리입니다. `stays` 가 비었을 때
`excludedSoldOut > 0` 이면 조회는 성공했고 전부 만실이라는 뜻이고, `partial: true` 면 일부
공급사를 못 봤다는 뜻입니다. 둘은 다른 상황이므로 클라이언트가 구분할 수 있어야 합니다.

### 검색 전체에도 상한을 둔다

어댑터의 응답 제한(3초)은 **묶음 하나**에 걸립니다. 숙소가 늘어 묶음이 많아지면 합은 그보다
길어질 수 있으므로, 검색 전체에 별도 상한(기본 5초)을 둡니다.

상한을 넘기면 **그때까지 도착한 묶음만으로 응답**하고, 못 받은 공급사는 타임아웃으로 표시합니다.
전부 버리고 오류를 주면 늦은 공급사 하나가 전체를 없애는 셈입니다. 부분 실패를 허용하기로 한
이상, 늦어서 못 받은 것도 같은 방식으로 다뤄야 합니다.

**실패의 실제 단위는 공급사가 아니라 (공급사 × 요청 묶음)입니다.** 숙소 코드를 50개씩 나눠
호출하므로, 한 공급사의 여러 묶음 중 일부만 실패할 수 있습니다. 내부적으로는 묶음 단위로
집계하되, 고객에게 노출하는 단위는 공급사로 단순화합니다. 묶음은 우리 내부 구현 사정이지
고객이 알 일이 아닙니다.

## 조회 흐름

공급사는 **지역으로 검색해주지 않습니다.** 조회할 숙소 코드를 우리가 정해서 넘겨야 합니다.
그래서 성격이 다른 두 API 를 다르게 다룹니다.

| | 성격 | 우리 쪽 처리 |
| --- | --- | --- |
| 숙소 목록 | 정적 콘텐츠. 자주 안 바뀜 | 미리 조회해 **매핑을 DB 에 저장** |
| 재고·요금 | 호출할 때마다 달라짐 | **저장하지 않고 매번 조회** |

```
[사전] 공급사 숙소 목록 조회 → 내부 숙소·객실 타입으로 매핑 저장

고객 검색 요청 (날짜 · 인원)
 → DB 의 보유 숙소를 공급사별 코드로 묶음 (50개씩)
 → 공급사 재고·요금 병렬 조회 (WebClient)
 → 각 응답을 표준 모델로 정규화
 → 병합 (한쪽이 실패해도 나머지로 응답)
 → 통합 검색 결과 반환
```

### 숙소 목록을 언제 동기화하는가

**기동 시 1회 + 주기적 갱신 + 수동 트리거** 세 가지를 둡니다. 수동 트리거는
`POST /internal/suppliers/sync` 입니다(§동기화 확인해 보기).

검색할 때마다 호출하는 안은 버렸습니다. 자주 바뀌지 않는 정적 데이터를 매 요청마다 가져오는
것은 응답 지연과 호출 한도를 낭비합니다.

세 가지를 다 두는 이유는 각각이 메우는 구멍이 다르기 때문입니다. 기동 시 1회는 빈 DB 로 뜬
직후를, 주기적 갱신은 그 사이의 변화를, 수동 트리거는 **다음 주기까지 기다릴 수 없는 경우**를
맡습니다. 세 번째가 없으면 공급사에 숙소가 추가됐을 때 할 수 있는 일이 재기동뿐입니다.

중요한 건 **동기화 실패가 검색 실패로 번지지 않는 것**입니다. 기동 시 동기화가 실패해도
애플리케이션은 뜨고, 이미 저장된 매핑으로 검색을 계속 서빙합니다. 매핑은 우리 DB 에 있으므로
공급사가 죽어 있어도 "무엇을 물어볼지"는 알고 있습니다. 이 약속은 문서에만 두지 않고, 닿지
않는 주소를 물려 기동시키는 테스트로 고정했습니다.

### 목록에서 사라진 숙소를 지우지 않는 이유

동기화는 **새로 나타난 코드를 추가할 뿐, 목록에서 빠진 코드를 지우지 않습니다.**

공급사가 그 숙소를 접은 것과, 목록 API 가 일시적으로 그 숙소를 빠뜨린 것은 응답만으로 구분되지
않습니다. 지우는 쪽을 택하면 후자일 때 내부 식별자가 사라지고, 다시 나타났을 때 새 식별자를
받게 됩니다. **"같은 공급사 상품은 언제 조회해도 같은 내부 식별자"** 라는 이 시스템의 유일한
보장이 그 순간 깨집니다.

대가는 팔지 않는 숙소의 매핑이 남는다는 것입니다. 그 행은 검색할 때 공급사에 물어보는 코드가
하나 늘어나는 비용이고, 재고·요금 응답에 안 잡히면 결과에도 안 나옵니다. 잘못 지우는 비용보다
싸다고 봤습니다. 정리가 필요해지면 "몇 회 연속으로 목록에 없었는가" 같은 기준을 따로 두는 편이
맞고, 그건 지금 판단할 수 있는 문제가 아닙니다.

### 숙소가 수천 개가 되면

재고·요금 API 는 한 번에 최대 50개 숙소 코드를 받습니다. 지금 데이터로는 걸리지 않지만
구조는 미리 잡아둡니다.

- 공급사별 코드를 **50개 묶음으로 분할**하고, 묶음마다 병렬 호출
- 묶음 단위로 부분 실패를 허용 (일부 묶음이 실패해도 나머지 묶음 결과는 살림)
- 묶음 수가 늘면 공급사별 **동시 호출 수에 상한**을 둠. 상한 없이 병렬로 띄우면 우리가
  공급사를 공격하게 되고 호출 한도에 걸립니다

다만 숙소가 수천 개인 상황에서 **매 검색마다 전체를 조회하는 구조 자체가 한계**입니다.
검색 조건이 날짜·인원뿐이라 후보를 좁힐 축이 없기 때문입니다. 이 규모에서는 요금·재고 캐시
(짧은 TTL)나 사전 조회로 방향을 바꿔야 하고, 그때는 "재고를 저장하지 않는다"는 현재 원칙을
다시 검토해야 합니다. 현재 구현 범위에서는 다루지 않습니다.

## 저장 정책

요금·재고의 **원본은 외부에 있으므로 저장하지 않습니다.** 저장하는 순간 원본과 어긋날 수 있고,
그 오차를 관리하는 비용이 생깁니다. 저장하는 것은 **공급사 코드와 내부 식별자의 매핑뿐**입니다.

| 매핑 | 키 | 값 |
| --- | --- | --- |
| 숙소 | (공급사, 공급사 숙소 코드) | 내부 숙소 식별자 |
| 객실 타입 | (공급사, 공급사 숙소 코드, 공급사 객실 타입 코드) | 내부 객실 타입 식별자 |

객실 타입 코드는 **해당 숙소 안에서만 유일**합니다. 다른 숙소에 같은 코드가 존재할 수 있으므로,
객실 타입을 유일하게 가리키려면 숙소 코드가 키에 함께 들어가야 합니다.

**두 매핑 모두 위 키 조합에 unique 제약을 겁니다** — 숙소는 두 값, 객실 타입은 세 값입니다.
이 제약이 "같은 공급사 상품은 언제 조회해도 같은 내부 식별자로 돌아온다"를 보장하는 장치입니다.

### 무엇으로 저장하는가

**H2 를 `JdbcClient` 로 씁니다.** 스키마는 [schema.sql](src/main/resources/schema.sql) 이
소유합니다.

ORM 을 얹지 않은 이유는 이 DB 가 할 일이 좁기 때문입니다. 테이블이 둘이고 그 사이에 관계가
없으며(객실 타입이 숙소 코드를 키에 이미 들고 있어 참조로 이을 이유가 없습니다), 쓰기는
upsert 하나, 읽기는 전체 조회 둘입니다. 이 규모에서 ORM 이 줄여주는 코드가 거의 없는 반면,
**내부 식별자 안정성을 보장하는 unique 제약이 스키마 파일에 그대로 보인다**는 이점은 분명합니다.
설계 문서가 그 제약을 보장 장치로 내세웠으니, 그것이 생성 전략 뒤에 숨지 않는 편이 낫습니다.

대가도 적어 둡니다. upsert 에 쓴 `MERGE ... KEY` 는 H2 문법이라, 다른 DB 로 옮기면 그 두 문장을
바꿔야 합니다. 바꿀 자리가 저장소 구현 한 곳뿐이라는 것을 알고 택했습니다.

**메모리가 아니라 파일(`./data/`)로 둡니다.** 기동 시 동기화가 실패해도 이미 저장된 매핑으로
검색을 계속 서빙한다는 것이 위 설계인데(§숙소 목록을 언제 동기화하는가), 메모리로 두면 재기동
때마다 그 전제가 사라져 문서와 코드가 어긋납니다.

### 이름을 저장하지 않는 이유

매핑 테이블에는 **식별자만** 있습니다. 숙소명·객실 타입명·최대 수용 인원은 두지 않습니다.

그 값들은 재고·요금 응답에 매번 실려 옵니다. 매핑 행에도 복사해 두면 같은 값의 출처가 둘이
되고, 둘은 언젠가 어긋납니다. 그때 무엇을 믿을지를 또 정해야 하는데, 그 비용을 치를 만큼
얻는 것이 없습니다. 저장하는 것은 **정체**뿐이고 내용은 매번 공급사에서 옵니다.

잃는 것도 있습니다. 공급사 목록에는 있지만 검색 결과에 잡히지 않은 숙소는 이름을 알 방법이
없습니다. 지금 계약(검색 결과에 담기는 숙소는 모두 재고·요금 응답에서 온다)에서는 문제가
되지 않지만, "우리가 취급하는 숙소 목록"을 보여주는 기능이 생기면 이 결정을 다시 봐야 합니다.

## 신규 공급사 추가 방법

공급사를 추가할 때 **어댑터 구현체만 추가**하면 되고, 도메인·검색 로직은 수정 대상이 아닙니다.

1. 공통 어댑터 인터페이스를 구현하는 클래스를 `adapter` 패키지 아래 추가한다
2. 그 공급사 전용 요청/응답 DTO 를 같은 패키지 안에 두고 **밖으로 노출하지 않는다**
3. 응답 → 표준 모델 변환을 별도 매퍼로 분리한다
4. 그 공급사의 실패 판정(상태 코드 기반이든 본문 코드 기반이든)을 공통 실패 타입으로 정규화한다
5. base URL·인증 키·타임아웃을 설정에 추가한다

검색 로직은 등록된 어댑터 목록을 순회할 뿐 각 공급사를 알지 못하므로, 위 다섯 단계 외에
고칠 곳이 없습니다. 계층별로 무엇을 알고 무엇을 모르는지는
[docs/architecture.md](docs/architecture.md) 에 정리해 두었습니다.

**단계별 시그니처와 실제 파일 목록, 빠뜨리기 쉬운 것은
[docs/adding-supplier.md](docs/adding-supplier.md) 에 있습니다.**

**이건 주장이 아니라 실측입니다.** 공급사 B 를 붙이면서 늘어난 것은 `adapter/b/` 패키지 다섯
파일과 `application.yaml` 의 `supplier.b.*` 블록뿐이고, **`domain`·`port`·`application`·`api`
운영 코드는 한 줄도 바뀌지 않았습니다.** B 가 A 와 요금 표현도(총액만) 실패 통지 방식도(200 +
본문 코드) 다르다는 점에서, 흡수해야 할 차이가 실제로 있는 상태에서 확인한 결과입니다.

## API

```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

검색 조건은 **날짜와 인원뿐**이고, 조회 대상은 보유 숙소 전체입니다. 공급사가 지역 정보를
주지 않으므로 지역·키워드 필터는 다루지 않습니다.

체크아웃일은 숙박일에 포함되지 않습니다 (09-01 체크인 / 09-04 체크아웃 = 3박).

**필드별 타입·필수 여부·에러 목록은 [docs/api.md](docs/api.md) 에 있습니다.** 여기서는 무엇을
왜 그렇게 정했는지만 다룹니다.

**인원은 기본값으로 채우지 않습니다.** 몇 명이 묵는지는 요금과 재고 판정에 모두 영향을 주는
값이라, 안 보냈을 때 우리가 정하면 묻지도 않은 조건으로 검색해 준 셈이 됩니다. `adults` 가
없으면 400 입니다. 조건이 성립하지 않는 경우(체크아웃이 체크인보다 앞, 성인 0명, 날짜 형식
오류)도 400 이고, 판단은 도메인 타입이 생성 시점에 합니다.

응답에는 내부 숙소 식별자·숙소명, 내부 객실 타입 식별자·객실 타입명, 최대 수용 인원,
예약 가능 객실 수, 출처 공급사, 조식 포함 여부, 요금 정보가 담깁니다. 여기에 더해 일부 공급사
조회가 실패했다면 그 사실(`partial`, `suppliers`)과 제외 건수 셋을 함께 반환합니다.
응답 형태는 §부분 실패 허용의 예시를, 제외 건수의 뜻은 §무엇을 왜 뺐는지를 보세요.

세액과 날짜별 내역은 **주는 공급사에서만** 채워집니다. 없으면 0 이나 빈 배열이 아니라 필드
자체가 나가지 않습니다 — 없는 것을 0 으로 내보내면 "0원"과 구분되지 않습니다.

## Mock Supplier

실제 공급사를 호출하지 않습니다. 스펙을 흉내내는 Mock 을 **별도 포트(9090)** 로 띄웁니다.

애플리케이션과 같은 포트에 두면 자기 자신을 HTTP 로 호출하게 되어, 스레드가 묶이면서 연동
문제로 오해하기 쉬운 실패가 생깁니다.

Mock 은 세 상황을 재현할 수 있어야 합니다.

| 상황 | 용도 |
| --- | --- |
| 정상 응답 | 기본 흐름 검증 |
| 공급사 장애 | 실패 판정 통일 검증 (A 는 5xx, B 는 200 + 실패 코드) |
| 무응답 | 타임아웃·부분 실패 검증 |

정상 응답만 재현할 수 있으면 타임아웃과 부분 실패가 실제로 동작하는지 보일 수 없습니다.
이 셋이 있어야 견고성 설계가 검증됩니다.

`mock-supplier` 서브프로젝트가 이를 구현합니다. 요청 파라미터는 무시하고 고정 응답을 주며,
런타임에 모드를 바꿔 고장을 재현합니다.

```bash
curl -X POST 'http://localhost:9090/control/a/mode?value=no-response'  # A 무응답
curl -X POST 'http://localhost:9090/control/b/mode?value=error'        # B 장애
curl -X POST 'http://localhost:9090/control/a/mode?value=normal'       # 정상 복귀
```

장애 모드에서 두 공급사가 **서로 다르게** 실패한다는 점이 핵심입니다. 실측 결과입니다.

| 공급사 | 장애 모드 응답 |
| --- | --- |
| A | `HTTP 503` + `{"error":"SERVICE_UNAVAILABLE", ...}` |
| B | **`HTTP 200`** + `{"resultCode":"E503", "data":null}` |

어댑터가 이 둘을 같은 실패로 정규화하는지 확인하려면 Mock 이 차이를 그대로 재현해야 합니다.

숙소 목록 API 에는 장애 모드를 걸지 않았습니다. 매핑을 만드는 단계가 실패했을 때의 처리는
검색 경로의 부분 실패와 성격이 다른 주제라 분리했습니다(§숙소 목록을 언제 동기화하는가).

`adding-supplier.md` 는 **B 를 붙인 뒤에 썼습니다.** 미뤄둔 이유가 그것이었습니다 — 붙이기
전에 썼으면 "이렇게 될 것이다"가 되고, 그건 검증되지 않은 절차입니다. 지금 문서에 적힌 파일
목록과 줄 수, 빠뜨리기 쉬운 것 일곱 가지는 전부 실제로 밟은 경로에서 나왔습니다.

`integration-model.md` 도 같은 이유로 B 뒤에 썼습니다. 공급사별 대응표는 절반이 B 라, 붙기
전에는 절반이 빈 표가 됩니다.

**`observability.md` 는 지표를 붙이지 않은 채 썼습니다.** 위 둘을 미뤄둔 이유와 어긋나는 선택이라
그대로 두지 않고, **현재 상태는 전부 실측으로 확인하고 앞으로의 모양만 설계로 적는** 방식으로
갈랐습니다. 문서 안에서 ✅ 실측과 ○ 설계를 표기로 구분합니다.

그렇게 나눠 보니 **설계보다 실측 쪽에서 나온 것이 많았습니다.** 시간을 재는 코드가 운영 코드에
하나도 없어 응답 지연은 원천 데이터가 0 이고, 성공 경로에 로그가 없어 성공률은 분모가 없으며,
연결 타임아웃이 `TIMEOUT` 이 아니라 `SUPPLIER_ERROR` 로 분류되고 있었습니다(닿지 않는 주소로 실제
호출해 확인했습니다). **셋 다 "지표를 어떻게 붙일까"를 적으려다 나온 것이지, 코드를 읽어서 나온
것이 아닙니다.** 마지막 것은 지표 이전에 응답의 `reason` 값이 지금 틀리다는 뜻이라 열린 문제로
옮겼습니다.

**AI 활용 기록은 [JOURNAL.md](JOURNAL.md) 의 각 일자 `AI 활용` 절에 있습니다.** 무엇을 받아들이고,
무엇을 고치고, 무엇을 거부했는지를 남겼습니다.

연동 견고성(타임아웃 산정 근거, 실패 판정 통일, 부분 실패)은 별도 문서를 두지 않고 위
§연동 견고성 에서 다룹니다. 재시도·서킷 브레이커를 실제로 설계하게 되면 그때 문서를 나눕니다.
